# Expo 스캐폴딩 — 배포 형태부터 이해하고 시작하기

> Phase 3 착수. `mobile/` 신규. 관련 결정: D-027(직접 개발), D-028(SDK 54 고정), D-029(위치·식별자).
> 백엔드는 해봤지만 프론트/모바일은 처음인 상태를 전제로 쓴다.
> "무엇을 깔았는지"보다 **"이 판이 어떻게 굴러가는지"** 를 먼저 잡는 게 목적이다.

## 0. 가장 먼저 풀어야 할 오해: 사용자도 Expo를 깔아야 하나?

**아니다.** 이 오해가 풀려야 나머지가 이해된다. 이름이 비슷한 세 가지를 구분해야 한다.

| 이름 | 정체 | 누가 설치하나 |
|---|---|---|
| **Expo** | React Native 위에 얹는 개발 프레임워크·툴체인 | 아무도 안 깖 (개발 도구) |
| **Expo Go** | 개발 중 코드를 즉석에서 열어보는 **뷰어 앱** | 개발자만. 출시 후엔 무관 |
| **빌드 결과물** | 우리 아이콘·이름을 단 독립 `.aab`/`.ipa` | **사용자** — 스토어에서 "엠마오" 설치 |

서버 개발에 비유하면 이렇다:

```
mvn spring-boot:run   →  로컬에서 띄워 확인       ≒  Expo Go
.jar 말아서 서버 배포  →  사용자가 접속하는 실체   ≒  스토어 빌드
```

`mvn spring-boot:run`으로 개발한다고 해서 사용자가 Maven을 깔지 않는 것과 같다. 출시 때는
`eas build`로 **엠마오라는 독립 앱 파일**을 만들어 스토어에 올리고, 그 안에 Expo Go는 존재하지 않는다.
홈 화면 아이콘도 우리 아이콘이다.

덧붙여, "Expo를 쓰면 네이티브 기능에 제약이 있다"는 말은 몇 년 전 이야기다. 예전 Expo는 미리 정해진
네이티브 모듈만 쓸 수 있었지만, 지금은 **개발 빌드**가 생겨 카카오 SDK 같은 임의의 네이티브 모듈도
넣을 수 있다. 결과물이 평범한 네이티브 앱이라 스토어 심사에서도 불이익이 없다.

## 1. 실행 방식이 3단계로 바뀐다

이게 이 문서의 핵심이다. 모바일은 **개발 단계마다 앱을 실행하는 방식이 달라진다.**

| 단계 | 실행 방식 | 특징 | 한계 |
|---|---|---|---|
| UI 제작 | **Expo Go** + QR | 설치 없이 즉시. 저장하면 바로 반영 | 네이티브 모듈 못 씀 |
| 로그인 붙일 때 | **개발 빌드** | 우리 앱 껍데기를 폰에 설치 | 빌드 시간 필요 |
| 출시 | **프로덕션 빌드** | 스토어 업로드용 | — |

왜 중간에 갈아타야 하나? **카카오 로그인은 Expo Go에서 절대 안 돌아간다.** 카카오 SDK는 네이티브
코드(Java/Kotlin, Swift)인데, Expo Go는 미리 컴파일된 앱이라 우리가 나중에 추가한 네이티브 코드가
그 안에 들어있을 수 없다. 자바로 치면, 이미 빌드된 `.jar`에 새 클래스를 런타임에 끼워넣으려는 것과 같다.

그래서 순서를 **UI 먼저, 로그인 나중**으로 잡았다. 편한 Expo Go 루프를 최대한 오래 쓰기 위해서다.

## 2. SDK 버전이 폰과 묶여 있다 (이번에 데인 부분)

스캐폴딩하면서 실제로 막혔던 지점이라 남긴다.

**증상**: QR을 찍으니 `Project is incompatible with this version of Expo Go / requires a newer version`.
Play스토어에서 방금 설치한 최신 Expo Go인데도 그랬다.

**원인**: Expo는 SDK를 통째로 올리는 방식이고, **Expo Go는 한 시점에 하나의 SDK만 지원한다.**
그런데 `create-expo-app@latest`가 갓 배포된 SDK 57로 프로젝트를 만들었고, 폰에 깔린 Expo Go는
SDK 54 세대(앱 버전 54.0.8)였다. 기기·OS 사정에 따라 Play스토어가 최신이 아닌 빌드를 내려주기도 한다.

**진단 방법** — 에러 문구의 방향을 읽으면 된다:

| 문구 | 뜻 | 조치 |
|---|---|---|
| requires a **newer** Expo Go | 프로젝트 SDK > Expo Go | 프로젝트를 내리거나 Expo Go 업데이트 |
| requires an **older** Expo Go | 프로젝트 SDK < Expo Go | 프로젝트를 올림 |

npm에서 어떤 SDK가 살아있는지는 이렇게 본다:

```bash
npm view expo dist-tags
# latest / next / sdk-54 / sdk-55 ... 태그별 버전이 나온다
```

**시도해서 실패한 방법**: `npm install expo@~54` 후 `npx expo install --fix`.
56→54처럼 두 세대를 건너뛰니 React·expo-router의 peer dependency가 서로 안 맞아 ERESOLVE로 터졌다.

**성공한 방법**: 해당 SDK 템플릿으로 **재생성**.

```bash
npx create-expo-app@latest mobile --template expo-template-default@sdk-54
```

교훈은 일반적이다 — **의존성 그래프를 억지로 끌어내리는 것보다, 정합성이 보장된 조합으로 다시
만드는 게 싸다.** 프로젝트 초기라 우리 코드가 화면 1개뿐이었기에 가능한 선택이기도 하다.
(SDK 54 고정은 임시다. 개발 빌드로 넘어가면 Expo Go 제약이 사라지므로 그때 최신으로 올린다 — D-028)

## 3. expo-router — 파일이 곧 경로

Spring의 `@GetMapping("/chat")`에 해당하는 걸 **파일 위치**로 표현한다.

```
app/_layout.tsx   → 공통 껍데기(네비게이션). 모든 화면을 감쌈
app/index.tsx     → "/"     첫 화면
app/chat.tsx      → "/chat"
app/login.tsx     → "/login"
```

컨트롤러에 메서드를 추가하듯, `app/`에 파일을 만들면 그게 곧 화면 하나다. 라우팅 설정 파일을
따로 관리할 필요가 없다.

**Stack을 골랐고 Tabs를 버린 이유**: 기본 템플릿은 하단 탭 UI로 온다. 하지만 엠마오는
`로그인 → 채팅`처럼 **쌓였다 돌아오는** 흐름이라 Stack(화면을 쌓는 방식)이 맞다.
탭은 대등한 화면을 오갈 때 쓴다. 템플릿의 데모 화면은 `reset-project` 스크립트로 걷어내
`app-example/`에 참고용으로 남겼다(gitignore 대상이라 레포엔 안 올라간다).

## 4. 아이폰은 맥 없이 되나 — 된다, 조건 셋

Windows에서 개발 중이라 실제로 걸리는 문제다.

1. **코드는 그대로 간다.** RN 단일 코드베이스라 안드로이드로 짠 화면이 iOS에서도 동작한다.
2. **빌드는 EAS Build(클라우드)** — Expo 쪽 맥 서버가 iOS 빌드를 대신 돌려준다. 맥 불필요.
   단 Apple Developer 계정($99/년)이 필요하다.
3. **리스크 두 가지**:
   - **iOS 실기 검증은 출시 전 반드시 한 번 필요하다.** Windows에선 iOS 시뮬레이터를 못 돌려서
     안전영역(노치)·키보드 동작·폰트가 안드로이드에서만 맞고 iOS에서 깨질 수 있다.
   - **iOS에 내려면 애플 로그인 구현이 사실상 필수다.** 애플 심사 가이드라인 4.8상, 구글·카카오
     소셜 로그인을 제공하면서 애플 로그인만 빼면 리젝 사유가 된다. 안드로이드 선출시에는 지장 없다.

## 5. 검증을 어떻게 했나

UI는 "돌려봐야 안다"가 맞지만, 폰을 집어들기 전에 기계적으로 걸러낼 수 있는 것들이 있다.

```bash
npx tsc --noEmit                      # 타입 에러
npx expo-doctor                       # 의존성 버전 정합성 (18개 검사)
npx expo export --platform android    # 번들이 실제로 만들어지는지
```

세 개가 다 통과해도 **"화면이 제대로 보이는지"는 검증하지 못한다.** 그래서 마지막에 반드시
Expo Go 실기동으로 눈으로 확인한다(D-027). 백엔드에서 단위 테스트가 통과해도 통합 환경에서
깨질 수 있는 것과 같은 구조다 — 자동 검증은 **범위를 좁혀줄 뿐 대체하지 못한다.**

참고로 `app-example/`은 `@/` 별칭이 어긋나 타입 에러를 대량 뱉는다. 참고용 코드일 뿐이라
`tsconfig.json`의 `exclude`에 넣어 검사 대상에서 뺐다.
