# 탭과 옵트인 저장 — 화면 구조와 데이터 책임을 함께 바꾸기

> 2026-08-17 구현, 2026-08-22 검증. 관련 결정: D-040·D-041.
> 이 장은 홈 화면과 하단 탭을 추가하면서 화면 구조가 어떻게 바뀌었는지, 그리고
> 마음 기록·기도 제목·보관함을 왜 "사용자가 직접 저장한 것만" 남기도록 설계했는지를 다룬다.

---

## 1. 화면 하나를 추가하는 일과 앱의 뼈대를 바꾸는 일은 다르다

로그인 플로우까지의 앱은 `Stack`만 사용했다. 로그인하면 대화 진입 시트를 거쳐 채팅으로
가는 단순한 직선 흐름이었기 때문이다. 하지만 디자인 v1의 홈 화면에는 홈·말씀·바나바·
보관함·나, 다섯 공간을 오가는 하단 탭이 있었다. 홈 화면 하나만 그려 넣는다고 해결되는
문제가 아니었다. **앱의 최상위 이동 방식 자체를 Stack 중심에서 Stack과 Tabs의 조합으로
바꿔야 했다.**

두 내비게이터는 맡는 일이 다르다.

- `Stack`: 화면을 위에 쌓는다. 로그인, 모달, 전체화면 채팅처럼 앞뒤 흐름이 있는 화면에 맞다.
- `Tabs`: 같은 높이의 주요 공간을 옆으로 전환한다. 홈·말씀·보관함처럼 자주 오가는 화면에 맞다.

그래서 둘 중 하나만 고르지 않고 다음처럼 중첩했다.

```text
Root Stack
├─ (tabs)
│  ├─ 홈
│  ├─ 말씀
│  ├─ 바나바 → 대화 진입 시트로 이동
│  ├─ 보관함
│  └─ 나
├─ chat-entry       투명 모달
├─ chat             전체화면
├─ mind-record-new  투명 모달
└─ prayer-request-new
```

채팅을 탭 안에 넣지 않은 이유는 대화에 집중할 때 탭바가 계속 자리를 차지하지 않게 하기
위해서다. 바나바 탭을 누르면 `barnabas.tsx`가 콘텐츠를 그리지 않고 `/chat-entry`로 즉시
이동하고, 채팅은 Root Stack 위에 전체화면으로 열린다. 대신 채팅 화면에는 홈으로 돌아갈
버튼이 필요해졌다. 구조를 바꾸면 새 화면만 생기는 것이 아니라 **들어가는 길과 나오는 길을
함께 다시 설계해야 한다.**

## 2. "저장 기능"은 기술보다 정책이 먼저다

기존 결정 D-024는 대화 이력을 MVP에서 자동 저장하지 않는다는 것이었다. 신앙 상담에는
감정, 가족 문제, 교회 경험 같은 민감한 내용이 들어올 수 있다. 서버가 할 수 있다는 이유만으로
모든 대화를 보관하면 개인정보 범위와 삭제권, 미성년자 보호 같은 책임도 함께 커진다.

이번에 마음 기록·기도 제목·보관함을 추가한 것은 이 결정을 뒤집은 것이 아니다. 저장의
경계를 다음처럼 나눴다.

```text
사용자가 바나바와 대화함
└─ 자동 저장하지 않음

사용자가 마음 기록의 저장 버튼을 누름
└─ 그 기록만 저장

사용자가 바나바 답변의 북마크를 누름
└─ 그 대화 한 턴만 저장
```

핵심은 **옵트인(opt-in)**이다. 사용자가 명시적인 행동으로 저장 범위를 선택한다. 화면에서
버튼 하나를 추가한 것처럼 보이지만, 서버 입장에서는 "누가 어떤 데이터를 어떤 의사 표현으로
남겼는가"라는 제품 정책을 구현한 것이다.

마음 기록과 기도 제목도 별도 리소스로 나눴다. 두 데이터가 지금은 모두 짧은 텍스트처럼 보여도
의미와 화면 흐름이 다르다. 마음 기록에는 선택적인 `mood`가 있고, 기도 제목에는 없다. 하나의
범용 `notes` 테이블에 `type`만 넣는 방법도 있지만, 현재 필요한 두 개의 단순한 모델을 분리하는
편이 읽기 쉽고 검증 규칙도 명확하다. 아직 필요하지 않은 범용 추상화를 만들지 않은 선택이다.

## 3. JWT 인증과 데이터 소유권 검사는 서로 다른 방어선이다

`WebConfig`는 `/api/**` 요청 앞에 `JwtAuthInterceptor`를 둔다. 인터셉터는 JWT를 검증하고
토큰의 사용자 ID를 request 속성 `authUserId`에 넣는다. 컨트롤러는 이 값을 꺼내 서비스에
전달한다.

```java
public MindRecordResponse create(
        @RequestAttribute(name = JwtAuthInterceptor.USER_ID_ATTRIBUTE) String authUserId,
        @Valid @RequestBody MindRecordRequest request) {
    return MindRecordResponse.from(service.create(Long.valueOf(authUserId), request));
}
```

여기서 중요한 점은 요청 본문으로 `userId`를 받지 않는다는 것이다. 사용자가 JSON에 다른 사람의
ID를 넣어도 저장 대상을 바꿀 수 없게, **신원은 서버가 검증한 토큰에서만 가져온다.**

하지만 "로그인했다"와 "이 기록의 주인이다"도 같은 말은 아니다. 예를 들어 사용자가
`DELETE /api/mind-records/10`을 호출할 권한이 있는지는 10번 기록의 `userId`와 현재 JWT의
사용자 ID를 다시 비교해야 한다. 서비스 계층은 다음 두 단계를 모두 검사한다.

1. 해당 ID의 데이터가 존재하는가
2. 존재한다면 로그인한 사용자의 데이터인가

둘 중 하나라도 아니면 같은 `NotFoundException`을 반환한다. 다른 사람의 데이터가 실제로
존재하는지조차 알려주지 않는 방식이다. 목록 조회도 `findByUserIdOrderByCreatedAtDesc`처럼
처음부터 사용자 ID가 포함된 쿼리를 사용한다. **인증은 문을 통과시키고, 소유권 검사는 방 안의
물건을 만질 수 있는지 판단한다.** 둘 다 필요하다.

## 4. 보관함의 구절은 왜 다시 조회하지 않고 스냅샷으로 저장하나

바나바 답변에 붙는 구절 본문은 이미 채팅 파이프라인에서 `BibleVerseService`의 DB 검증을
통과했다. 보관함은 사용자가 그 순간 본 답변을 나중에도 같은 모습으로 다시 보는 기능이다.
따라서 주소만 저장하고 열 때마다 현재 DB에서 다시 조회하기보다, 저장 버튼을 누른 시점의
검증된 구절을 `verses_snapshot`에 JSON으로 남긴다.

```json
[
  {
    "reference": "누가복음 24:32",
    "text": "길에서 우리에게 말씀하시고 ..."
  }
]
```

별도 `archive_verses` 테이블로 정규화할 수도 있다. 하지만 지금은 구절별 검색이나 수정이
필요하지 않고, 보관 항목과 함께 통째로 읽고 쓴다. JSON 스냅샷은 이 접근 패턴에 맞는 가장
단순한 표현이다. 중요한 전제는 **모바일이 임의로 보낸 성경 본문을 새로 검증한 것으로 취급하는
경로가 아니라, 서버가 생성해 전달한 검증 결과를 사용자가 그대로 되돌려 저장하는 흐름**이라는
점이다. 향후 보관 API가 다른 입력 경로에도 공개되면 이 신뢰 경계는 다시 검토해야 한다.

## 5. DB 변경은 코드와 같은 버전으로 움직인다

세 기능은 Flyway 마이그레이션 세 개로 추가됐다.

| 버전 | 테이블 | 핵심 필드 |
|---|---|---|
| V4 | `mind_records` | `user_id`, `mood`, `content`, `created_at` |
| V5 | `prayer_requests` | `user_id`, `content`, `created_at` |
| V6 | `archive_items` | 질문, 답변, 구절 스냅샷, 생성 시각 |

JPA의 `ddl-auto`는 `validate`라서 애플리케이션이 테이블을 임의로 만들어주지 않는다. Flyway가
스키마를 바꾸고, JPA는 엔티티와 실제 스키마가 맞는지만 확인한다. 이 구분 덕분에 개발자마다
DB 모양이 달라지는 일을 막고, 어떤 버전에서 어떤 데이터 구조가 추가됐는지 기록으로 남긴다.

테스트도 레이어별로 나눴다.

- Repository 테스트: 사용자별 조회와 최신순 정렬
- Service 테스트: 생성과 소유권이 다른 삭제 거부
- Controller 테스트: JWT 요구, 입력 검증, 201·200·204 응답
- 전체 회귀 테스트: 기존 채팅·성경·위기·인증을 포함한 139건

새 기능 테스트만 통과하면 기존 안전 경로가 깨졌는지 알 수 없다. 그래서 마지막에는 전체
테스트를 실행했고, 모바일도 `tsc --noEmit`과 린트를 함께 통과시켰다.

## 6. 자동 생성 파일이 오래되면 올바른 코드도 틀렸다고 보일 수 있다

신규 모달 화면 두 개를 만든 뒤 TypeScript는 `/mind-record-new`와
`/prayer-request-new`가 존재하지 않는 경로라고 표시했다. 실제 파일은 있었지만 Expo Router의
`.expo/types/router.d.ts`가 이전 화면 목록을 담고 있었다. Expo 개발 서버를 한 번 시작해
라우트 타입을 재생성하자 소스 수정 없이 검사가 통과했다.

이 사례에서 배울 점은 **오류 메시지가 가리키는 코드와 오류의 원인이 항상 같은 위치에 있지는
않다**는 것이다. 타입이 "이 경로는 없다"고 말할 때 문자열을 강제 캐스팅해 조용하게 만들기보다,
그 타입이 어디에서 생성됐고 언제 갱신됐는지 확인해야 한다. 생성 파일을 최신화하는 것이 원인을
고친 것이고, 타입 검사를 우회하는 것은 증상만 숨기는 것이다.

## 정리 — 이 장에서 가져갈 것

1. Stack과 Tabs는 경쟁 관계가 아니라 역할이 다르며, 앱의 이동 구조에 맞게 중첩할 수 있다
2. 화면 구조를 바꾸면 들어가는 길뿐 아니라 뒤로 나오는 길도 함께 설계해야 한다
3. 민감한 데이터는 "저장할 수 있는가"보다 "어떤 사용자 행동을 저장 동의로 볼 것인가"를 먼저 정한다
4. JWT 인증과 개별 데이터 소유권 검사는 서로 다른 방어선이다
5. 현재 조회 방식이 통째로 읽고 쓰는 것이라면 JSON 스냅샷이 별도 테이블보다 단순할 수 있다
6. 새 기능 테스트와 전체 회귀 테스트는 목적이 다르며 둘 다 필요하다
7. 자동 생성 타입이 오래됐을 때 강제 캐스팅으로 우회하지 말고 생성 과정을 갱신한다
