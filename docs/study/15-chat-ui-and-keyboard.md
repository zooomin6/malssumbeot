## 1. 라이브러리를 쓸까 직접 만들까 — 판단 기준

7/27에 `@kesha-antonov/react-native-chat`을 채택했다가 8/3에 걷어냈다. 변덕이 아니라,
**붙여보려는 순간에야 드러나는 정보**가 있었기 때문이다.

판단에 쓴 질문은 두 개다.

**질문 1 — 이 라이브러리가 주는 것 중 우리가 쓰는 건 몇 %인가?**

목록을 뽑아보니 이미지·동영상·음성 메시지, 이모지 리액션, 답장, 아바타, 읽음 표시, 스트리밍
커서가 들어 있었다. 우리가 쓰는 건 **텍스트 말풍선 하나**였다.

**질문 2 — 제품의 차별점이 라이브러리 안에 있나?**

없었다. 엠마오의 채팅 화면에서 특징적인 건 **구절 인용 카드**인데, 이건 어느 채팅
라이브러리에도 없다. 즉 라이브러리를 써도 핵심은 직접 만들어야 하고, 그마저도 남의 말풍선
**안에** 억지로 끼워 넣어야 했다.

두 답을 합치면 결론이 나온다. 이 라이브러리는 도움이 아니라 **제약**이었다.

### 그럼 직접 만들면 뭐가 어려운가

여기서 중요한 건 "직접 만들기의 난이도"를 정직하게 따지는 것이다. 필요한 조각은 넷이었다.

| 조각 | 난이도 |
|---|---|
| 메시지 목록 | RN 기본 `FlatList`로 끝 |
| 말풍선 | 사각형에 글씨. 쉬움 |
| 입력창 + 전송 | 쉬움 |
| **키보드 회피** | **여기가 유일한 난관** |

그리고 결정적인 사실 하나 — 키보드를 담당하는 `react-native-keyboard-controller`는
**그 채팅 라이브러리가 이미 의존성으로 끌고 들어온 패키지**였다. 즉 라이브러리를 걷어내도
가장 어려운 부분은 그대로 쓸 수 있었다. 이걸 확인한 순간 결정이 쉬워졌다.

> **교훈**: "직접 만들면 힘들다"고 뭉뚱그리지 말고 **조각으로 쪼개서 난이도를 매긴다.**
> 대개 어려운 건 한두 조각뿐이고, 그 조각만 다른 방법으로 해결되면 판이 뒤집힌다.

### `inverted` FlatList — 채팅 목록의 관용구

```tsx
<FlatList inverted data={messages} ... />
```

목록을 위아래로 뒤집어 그리는 옵션이다. 채팅에서 필요한 두 가지가 공짜로 해결된다.

- 새 메시지가 **아래에** 쌓이고 화면이 자동으로 따라간다
- 위로 스크롤하면 과거 메시지가 나온다

대신 데이터를 **최신이 배열 앞에** 오게 담아야 하고, `ListHeaderComponent`가 화면
**아래쪽**에, `ListFooterComponent`가 **위쪽**에 그려진다. 우리 코드에서 빠른 응답 칩이
header, "오늘" 날짜 칩이 footer인 건 그래서다.

## 2. 같은 이름의 컴포넌트가 둘 — 가장 찾기 어려웠던 버그

입력창을 누르면 화면이 과하게 밀려 올라갔다. 원인은 이것이었다.

```tsx
import { KeyboardAvoidingView } from "react-native";                    // ← 이걸 썼다
import { KeyboardAvoidingView } from "react-native-keyboard-controller"; // ← 썼어야 했다
```

**이름이 같다.** 타입 검사도 통과하고, 에디터도 아무 말 안 하고, 화면도 일단 그려진다.
자바로 치면 `@Override` 없이 메서드 이름에 오타를 내서, 컴파일은 되는데 호출만 안 되는 상황과 같다.

### 왜 하필 이 조합에서 터지나

RN 내장 `KeyboardAvoidingView`는 **안드로이드가 키보드에 맞춰 앱 창을 줄여주는 기본 동작**에
기대어 계산한다. 그런데 우리가 `_layout.tsx`에 넣은 `KeyboardProvider`가 **그 동작을 가져가서
직접 제어한다.** 그러면 내장 컴포넌트는 근거가 사라진 채로 값을 내게 된다.

즉 **각각은 정상인 두 부품이, 같이 쓰였을 때만 고장**나는 종류였다. 그래서 각 부품의 문서를
따로 읽어서는 안 나온다.

> **교훈**: 라이브러리가 "네이티브 동작을 대신 제어한다"고 하면, **그 동작에 의존하던 기존
> 코드가 조용히 망가진다.** 이건 그 라이브러리 문서에도 잘 안 적혀 있다.

## 3. 세 번 틀린 기록 — 그리고 왜 틀렸나

이 문제로 세 번 잘못된 처방을 냈다. 각각 다른 이유로 틀려서 남길 가치가 있다.

**1차 — 부호를 거꾸로 짚었다.** "헤더 높이를 이중으로 더하고 있다"고 보고 `keyboardVerticalOffset`을
지우라고 했다. 그랬더니 **아예 안 올라갔다.**

**2차 — 그 관측을 믿었다.** "안 올라간다"를 근거로 "값이 필요했구나" 하고 되살렸다. 그런데
**그때 쓰고 있던 컴포넌트가 이미 고장난 것**이었다. 고장난 자로 잰 값을 근거로 삼은 셈이다.

> **교훈**: **측정 도구가 고장났을 때의 관측은 정보가 아니다.** 실험 결과를 해석하기 전에
> "이 실험이 유효한 조건에서 이뤄졌나"를 먼저 물어야 한다. 이걸 건너뛰어서 한 바퀴를 헛돌았다.

**3차 — 방식 자체를 바꿨다.** 라이브러리 것으로 교체해도 여전히 과했다. 여기서 원인을 더
쫓는 대신 **계산 방식을 버렸다.**

`KeyboardAvoidingView` 계열의 계산식은 이렇다.

```js
keyboardY = 화면높이 - 키보드높이 - keyboardVerticalOffset
여백 = max(내뷰의_아래끝 - keyboardY, 0)
```

여기서 `내뷰의_아래끝`은 **컴포넌트가 스스로 측정한 값**이다. 이 값이 헤더를 포함하는지 아닌지가
화면 구성에 따라 달라지는데, **실기기 없이는 확인할 방법이 없었다.** 추측이 개입할 자리가 있는 한
계속 틀릴 수밖에 없는 구조였다.

그래서 그 계산을 통째로 없앴다.

```tsx
const { height } = useReanimatedKeyboardAnimation();   // 키보드가 열릴수록 음수
useAnimatedStyle(() => ({
  paddingBottom: Math.max(-height.value, insets.bottom),
}));
```

**키보드 높이를 직접 받아 그만큼만 여백을 준다.** 헤더도, 화면 위치도 식에 없다.
과하게 올라갈 수도, 안 올라갈 수도 없다.

> **교훈**: 원인을 못 잡겠으면 **추측이 들어갈 자리를 없애는 쪽으로 설계를 바꾼다.**
> "더 똑똑한 계산"보다 "틀릴 수 없는 계산"이 낫다. 특히 내가 직접 관측할 수 없는 환경에서는.

### `Math.max` 하나로 조건 분기를 없앤 것

- 키보드 닫힘 → `-height.value`가 0 → `insets.bottom`(하단 제스처바 여백)이 이긴다
- 키보드 열림 → 키보드 높이가 이긴다

`if (키보드 열렸으면 ...)` 같은 분기를 쓰면 그 경계에서 값이 **툭 튄다.** 하나의 식으로 묶으면
전환이 매끄럽다. 조건 분기를 줄이는 게 코드 미학의 문제가 아니라 **화면 품질의 문제**인 사례다.

## 4. 리렌더 vs UI 스레드 — "약간 느리다"의 정체

위치는 맞췄는데 입력창이 굼떴다. 처음 쓴 훅이 이것이었다.

```tsx
const isVisible = useKeyboardState((s) => s.isVisible);   // 순수 boolean
```

이 훅은 `keyboardDidShow`, 즉 **키보드 애니메이션이 끝난 뒤에** 값이 바뀐다. 그리고 값이
바뀌면 화면을 **다시 그린다.** 그래서 키보드가 다 올라온 다음에야 입력창이 따라붙었다.

바꿔 쓴 `useReanimatedKeyboardAnimation`은 성격이 다르다.

| | `useKeyboardState` | `useReanimatedKeyboardAnimation` |
|---|---|---|
| 값이 바뀌는 시점 | 애니메이션 **끝난 뒤** | **매 프레임** |
| 화면 갱신 방식 | 리렌더 (JS 스레드) | UI 스레드에서 직접 |
| 조건부 `style`에 쓸 수 있나 | 된다 | **안 된다** (리렌더를 안 일으킴) |
| 높이 부호 | 양수 | **음수** |

마지막 두 줄이 함정이다. 값이 안 바뀌는 것처럼 보이거나 방향이 반대로 나온다면 이 표를 의심하면 된다.

> **교훈**: 리액트에서 "값이 바뀌면 화면이 바뀐다"는 경로와, "애니메이션 값이 프레임마다
> 흐른다"는 경로는 **다른 길**이다. 부드러움이 필요하면 후자, 분기 판단이 필요하면 전자다.
> 이 둘을 섞으면 "코드는 맞는데 안 움직인다"가 된다.

## 5. 디자인 시안을 코드로 옮길 때 — 시각 언어를 먼저 읽는다

민규가 피그마로 만든 시안을 반영하면서 배운 게 있다. **색 값을 옮기는 것보다 "이 디자인이
무엇으로 무엇을 구분하는지"를 먼저 읽어야 한다.**

시안을 뜯어보니 규칙이 있었다.

- **테두리만 있고 안이 빈 것** = 말풍선이 아닌 것 → 첫 안내 문구, 빠른 응답 칩
- **채워지고 옅은 그림자가 있는 것** = 말풍선 → 바나바의 흰 말풍선

작업 중 "바나바 말풍선에 테두리를 넣으면 어떨까?"라는 이야기가 나왔는데, 넣지 않았다.
넣으면 바로 위에 있는 안내 문구와 **같은 종류처럼 보이기** 때문이다. 밋밋해 보였던 진짜 원인은
따로 있었다 — 시안에 있던 **그림자를 빠뜨린 것**이었다. 흰색과 크림색은 명도 차가 작아서
그림자가 없으면 경계가 뭉개진다.

```js
shadowColor: "#7a6a4a",   // 검정이 아니라 따뜻한 갈색
shadowOpacity: 0.08,
```

그림자 색을 검정이 아니라 배경과 같은 계열의 갈색으로 쓴 이유는, 크림색 배경 위에 회색
그림자를 얹으면 **탁해지기** 때문이다.

> **교훈**: 시안에서 옮겨야 할 건 색 값 목록이 아니라 **"어떤 시각 요소가 어떤 의미를 맡고
> 있는지"** 다. 그걸 모르면 나중에 요소를 추가할 때 남의 자리를 뺏게 된다.

## 6. 프론트 목업에서도 절대원칙 2는 지킨다

구절 카드에 넣을 목업 데이터를 만들면서 시편 13:1 본문을 **내 기억으로** 적을 뻔했다.
CLAUDE.md 절대원칙 2가 금지하는 바로 그 방식이다.

"목업이고 서버 붙으면 사라질 코드인데?"라고 넘길 수도 있었다. 하지만 그 상태로 폰에 띄우면
**검증 안 된 성경 본문이 화면에 표시된다.** DB가 꺼져 있어 대조도 불가능했다.

그래서 본문 자리를 자리표시자로 비웠다.

```tsx
verses: [{ verse: 6, text: "서버 연결 시 이 자리에 DB에서 조회한 개역한글 원문이 표시됩니다..." }]
```

구절 **주소**(`빌립보서 4:6-7`)는 그대로 뒀다. 주소는 DB로 검증 가능한 값이고, 지금 확인하려던
건 카드가 펼쳐지는 동작이라 화면 구성에는 영향이 없었다.

> **교훈**: 원칙은 "진짜 코드"에만 적용되는 게 아니다. **사용자 화면에 닿을 수 있는 모든 경로**에
> 적용된다. 그리고 원칙을 지키면서도 확인하려던 것을 확인할 방법은 대개 있다.

## 정리 — 이 장에서 가져갈 것

1. 라이브러리 판단은 **"우리가 쓰는 비율"과 "차별점이 그 안에 있나"** 두 질문으로 한다
2. "직접 만들면 힘들다"는 **조각으로 쪼개 난이도를 매기면** 대개 한두 조각 문제로 좁혀진다
3. 라이브러리가 네이티브 동작을 가져가면 **그 동작에 의존하던 기존 코드가 조용히 망가진다**
4. **고장난 도구로 잰 관측은 정보가 아니다** — 해석 전에 실험의 유효성을 먼저 묻는다
5. 원인을 못 잡겠으면 **추측이 개입할 자리를 없애는 설계**로 바꾼다
6. 부드러움은 리렌더가 아니라 **애니메이션 경로**에서 나온다
7. 시안에서 옮길 것은 색 값이 아니라 **시각 요소가 맡은 의미**다
